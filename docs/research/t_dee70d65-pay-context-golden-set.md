# Golden set: pay context and tier labels, incl. the US pay-transparency trap (t_dee70d65)

## Answer
55 real public postings (excerpt <= 600 chars each) labelled with the expected PLAN 5.1 `PayContext`, `remoteRegions` and the PLAN 5.3
branch (`listed_agnostic | us_legal_note_unknown | flat | adjusted | unknown`); 43 rows are `"judgment": true`. Plus 10 companies that
state a flat global pay policy and 10 that state location-based pay, each with a source URL (section "Company pay policies").
The JSON block at the bottom is ready to copy into `packages/pipeline/test/fixtures/golden/pay-context.json` (Phase 2 convention: golden sets test the *code*; the
`expected.payContext` object is what the extraction prompt should return and what `tier` takes as input).

Headline findings for the PM / dev cards:
1. **PLAN 5.3 has no branch for a listed range that is local to one country** (Mozilla, Tailscale, Grafana Singapore, an IDR range in Jakarta: rows gs-013, gs-017, gs-036, gs-054, gs-055). I labelled these `adjusted` (judgment). Decide whether `tier` should add a `listed_local` branch.
2. **The US trap is common and comes in several wordings** (12 rows): "range is for residents of the United States only" (GitLab, with the words "Remote-Global" in the same paragraph), "applies to US-based candidates only ... other regions determined based on location" (Consensys), "Base salary varies by location" under a "Pay Transparency Notice" heading (Coinbase), "ranges may differ for candidates in other locations" (Circle), "Salary range for US-based; local adjustments for other countries" (Seeq, HN), "market factors (such as location)" (Phantom).
3. **Flat-pay statements are almost never in the posting.** Only 3 of 55 postings say it (gs-020 a Jobgether client in its benefits line, gs-026 Supabase, gs-052 Kit). Every other flat company said it on a handbook, blog or careers page (section "Company pay policies"). This supports PLAN 5.2: the registry matters. Registry-driven rows are gs-025, gs-027, gs-053.
4. **Traps for the extractor** (not for the tier code): a placeholder range "100K - 999,999 USD" (gs-011); "EOR" in running text that is about what the employer sells, not how the hire is employed (gs-045, gs-047); IDR "58M" that the job board's structured field turned into "58-70 IDR" (gs-036); two currencies in one posting (gs-019, gs-024); text range and structured range that disagree (gs-039).
5. **UNKNOWN / not found** (what was tried is in "Gaps"): an engineering posting that pays in IDR; a posting that says the hire goes through Remote.com; an Indonesia-only frontend posting from a foreign company.

## How to read the labels
- `expected.payContext` is the PLAN 5.1 shape, exactly. Values come from the excerpt and the board's location field; `companyHq` is added only when well known (public company pages), otherwise omitted (all-remote companies have no HQ). Omitted `listedSalary` = the excerpt has no number.
- `hiringScope`: `worldwide` = nothing restricts the country; `region` = a named region or time-zone block; `countries` = a country list or a single country. A region/country list that does not include Indonesia or a region covering it means the location rules reject the row first; the row is still useful for tier tests, and `remoteRegions` carries the region codes as the board states them.
- `companyType` convention: `web3_protocol` = Web3-native company or lab whose product is a chain, wallet or on-chain infrastructure (Consensys, Phantom, Anza, Aptos, Alchemy, Ooga Booga); exchanges/issuers (Coinbase, Circle, Binance, Ledger) are `enterprise`. Both are judgments and flagged.
- `employment`: `eor` only when the posting says the hire is employed or paid through an EOR (Deel); EOR mentioned as something the employer sells is `employee`.
- `seniority`: Staff / Principal / Manager = `lead` (judgment, PLAN has only mid/senior/lead).
- `expected.branch` follows the PLAN 5.3 tree: range listed and shown to be location-agnostic -> `listed_agnostic`; range listed but US/legal note or location-dependent wording -> `us_legal_note_unknown`; no range: flat signals or registry says flat -> `flat`; adjusted signals or registry says adjusted -> `adjusted`; otherwise `unknown`. Rows with `registryPolicy` start from the registry (the posting alone would be `unknown`). A country-specific range with no US note is `adjusted` (see finding 1).

## How the JSON was checked against PLAN 5.1
A throwaway Zod script (`z.object({...}).strict()`, using the repo's own `zod` from `packages/pipeline/node_modules`) mirrors the PLAN 5.1 type field by field and validates every row's `expected.payContext`:
```
listedSalary?: { min?: number; max?: number; currency: string; period: "year"|"month"|"hour" }
hiringScope: "worldwide"|"region"|"countries"; regions?: string[]; indonesiaExplicit: boolean; companyHq?: string
companyType: "product"|"enterprise"|"web3_protocol"|"agency"|"talent_marketplace"|"unknown"
payPolicy: "location_agnostic"|"location_adjusted"|"unknown"; employment: "employee"|"contractor"|"eor"|"unknown"
seniority: "mid"|"senior"|"lead"|"unknown"
```
The row schema is also `.strict()`: `expected.branch` is one of the five PLAN 5.3 values, `excerpt.length <= 600`, `url` is a valid URL, ids are unique. Result on the final file: `rows 55, bad 0, judgment 43`. Listed numbers are visible in the excerpt for all rows except gs-038, gs-042, gs-049 (feed field only, noted in each row). `listedSalary.min` for gs-051 is in the excerpt as "$120-180k".
PLAN 5.1 has no field for "branch", "registryPolicy" or `feed`; those live outside `expected.payContext`.
