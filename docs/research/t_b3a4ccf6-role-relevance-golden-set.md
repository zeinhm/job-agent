## How the set was built
- Pulled once (a handful of polite requests, 2 s between requests, one host at a time) on 2026-10-09 from the public, logged-out feeds:
  - Remotive API: https://remotive.com/api/remote-jobs (accessed 2026-10-09)
  - RemoteOK API: https://remoteok.com/api (accessed 2026-10-09)
  - Himalayas API: https://himalayas.app/jobs/api and https://himalayas.app/jobs/api/search?q=... (queries: frontend engineer, react developer, next.js, web3 frontend, staff frontend; accessed 2026-10-09)
  - We Work Remotely RSS: https://weworkremotely.com/remote-jobs.rss and the front-end / full-stack / back-end category feeds (accessed 2026-10-09)
  - HN "Ask HN: Who is hiring? (October 2026)": https://news.ycombinator.com/item?id=49922569 (via https://hn.algolia.com/api/v1/search, accessed 2026-10-09). HN rows carry their comment id in `source`, e.g. `hn:49945147` = https://news.ycombinator.com/item?id=49945147.
- Titles are copied as published (company prefix removed for WWR, which formats as `Company: Title`). HN has no title field, so the role phrase from the comment's first line is used.
- `snippet` is at most 200 chars. It is a trimmed excerpt of the listing text where the feed gave one (Himalayas, HN), otherwise listing metadata (board category, location restriction) prefixed with the company name. Snippets are not full descriptions.
- Per-row source is the board key (`remotive`, `remoteok`, `himalayas`, `wwr`, `hn:<comment id>`); the feeds do not give a stable per-row URL that I recorded. Company is in the snippet. Listings expire, so rows may no longer be live; the golden set only needs the title and snippet text.
- The boards were light on senior frontend/Web3 titles in the plain feeds, so the Himalayas search endpoint and the HN thread were used to top up. Remotive's `search=` and RemoteOK's `tag=` parameters are ignored by the API (results unchanged), so they did not help.

## Labelling rules applied (from phase-2-conventions.md "Role relevance")
- `keep`: senior frontend / software / full-stack engineer incl. Web3; React, TypeScript, Next.js, frontend platform; senior IC; lead / staff / principal; an out-of-target engineering title that also contains a target keyword (e.g. "Full-Stack (React/Node)").
- `reject`: non-engineering roles (legal, medical, sales, marketing, support, design, PM, ops, HR); explicit junior / intern / trainee / graduate roles (even when the stack matches); backend-only, mobile-only, data/ML, DevOps/SRE/infra, QA, security engineering.
- `unclear`: engineering titles with no stack or domain in the title ("Staff Software Engineer", "Member of Technical Staff", "Product Engineer", "Design Engineer"), where the rule says keep and flag `role_unclear`. The resolve stage decides later from the extraction.
- Location is out of scope here: a keep row can still be location-rejected by the other rules.

## Judgment calls worth the owner's attention
- `React Native` / `Flutter` titles are mobile-only and rejected even though "React" is a target keyword (rl-063, rl-064, rl-065). A naive keyword match would keep them. Decision needed on whether "React Native" should count as a target.
- Non-React frontend/full-stack titles (Angular, Vue/Nuxt, .NET, Rails, Fiori) are kept because the title says frontend or full-stack and PLAN section 1 does not restrict to React (rl-022, rl-023, rl-024, rl-028, rl-035, rl-042).
- Frontend titles with no seniority word are kept (rl-002, rl-010, rl-012 and others). The owner targets senior roles, but the rule keeps "frontend" without a seniority requirement.
- Generic `Software Engineer` / staff / principal / lead titles with no stack: `unclear`, not keep (rl-094 to rl-102, rl-107, rl-108).
- Multi-role listings that include a target role (rl-114, rl-115) are `unclear`; the rule has no case for them.
- Security software engineering, Shopify, and "Product Engineer (PM role)" are rejected as outside the target (rl-067, rl-068, rl-069).
- Fullstack Web3 with Solidity/Rust (rl-017) is kept because of Fullstack + TypeScript + Web3.
