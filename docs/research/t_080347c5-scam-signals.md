## 2. Domain age (free, no login)

**Method (tested 2026-10-09):**
1. Download the IANA bootstrap file `https://data.iana.org/rdap/dns.json` (JSON, `"version":"1.0"`, `"publication":"2026-09-30T23:00:03Z"`, `services` = list of `[[tlds],[rdapBaseUrls]]`). Cache it for 24 h. Longest-suffix match on the domain's TLD.
2. `GET <base>domain/<registrable-domain>`. Tested: `https://rdap.verisign.com/com/v1/domain/anthropic.com` returned `events` with `{"eventAction":"registration","eventDate":"2001-10-02T18:10:32Z"}` (that was the response shape; fetched for the example domain it listed `registration`, `expiration`, `last changed`, `last update of RDAP database`). Use `registration` only; `last changed` moves on every renewal.
3. Domain age = now - registration date. Cache per registrable domain for 30 days in the DB (domains are per company, not per posting, so volume is tiny).

**Bootstrap entries seen in the file:** `com` -> rdap.verisign.com/com/v1/, `xyz` -> rdap.centralnic.com/xyz/, `ai` -> rdap.identitydigital.services/rdap/, `id` -> rdap.pandi.id/rdap/, `app` and `dev` -> pubapi.registry.google/rdap/, `org` -> rdap.publicinterestregistry.org/rdap/. **No entry for `io` and `co`** (read through a summarising fetcher, so confidence medium; the dev card should assert it with `jq '.services[] | select(.[0][] == "io")' dns.json`). `rdap.nic.io` did not resolve from this machine (`ENOTFOUND`). `.io` and `.co` are very common for startups and Web3, so a real share of company domains will have unknown age.

**rdap.org (the public redirector):** documented limit "a maximum of 10 requests in 10 seconds" (Cloudflare), 302 with `Location` to the registry, 404 when no authoritative server is registered with IANA, 429 when rate limited, 403 when blocked for abuse. **I could not test it: `https://rdap.org/domain/example.com` returned 403 to the research fetcher** (UA/IP blocked, not verified why). So do not depend on rdap.org: read the bootstrap file directly (RFC 9224) and query the registry. Registry servers have their own limits (not published in the Verisign response; its `notices` only mention "Terms of Use"). Use 1 request per 2 s per host, one retry on 429 honouring `Retry-After`, a descriptive User-Agent, and a 5 s timeout.

**TLDs without RDAP, or lookup failure:** set `domainAgeDays = null`, add 0 points, and show "domain age unknown". Optional second source (untested, UNKNOWN until tried): the Internet Archive CDX API `https://web.archive.org/cdx/search/cdx?url=<domain>&limit=1&output=json` gives the first capture date, a lower bound on site age, not on registration. A registry reply of 404 for a TLD that does have RDAP means the domain is not registered: +25 `domain_not_registered` (the posting's apply domain does not exist).

**Caveats for the rules:** registration date is not the site's real age (drop-catch re-registration resets it; old domains can be bought for fraud). Privacy redaction hides the registrant, not the dates. Treat age as a weak-to-medium signal, which is why no age score alone reaches 60.

## 3. Verification: "role also exists on the company's own ATS"

Existing adapters (`packages/sources/src/{greenhouse,lever,ashby}/index.ts`) fetch a whole board per configured company (`fetchBoard(company)` returns `RawPosting[]`, or `null` on 404 for an unknown slug) and the posting rows are already in the DB after `fetch`. So:

1. Input: a posting P from any source (board, HN, social) with a company name. Resolve the company in `config/companies.yaml`-backed `companies` table by normalised name or domain. No row, or no `ats_type`/slug -> verification result `unknown`, 0 points.
2. Look in `postings` for rows of that company from ATS sources (`greenhouse|lever|ashby`, later `smartrecruiters|workable|recruitee`) that were seen in the last 7 days. Zero requests.
3. Match: normalised title equal (lowercase, strip `(remote)`, locations, seniority synonyms, punctuation) or token Jaccard >= 0.8. Found -> `ats_verified` (-40). Board fetched OK today but no match -> `ats_missing` (+10; low weight because postings can be new, renamed, or a different team). Board missing (404) or fetch failed -> `unknown`.
4. Weak extra: P's own apply URL host is `boards.greenhouse.io`, `job-boards.greenhouse.io`, `jobs.lever.co`, `jobs.ashbyhq.com` and the slug equals the configured slug -> counts as verified. Anyone can create a board on these hosts, so a slug that does not match the configured company is *not* verified, and a never-seen slug claiming a known company's name is a `lookalike` (+30).
5. Do not query ATS boards for companies not in config (that would be guessing slugs; the earlier research needed about 50 slug guesses with many 404s).

Limit: this verifies *known companies*. A brand-new scam company is not in the config at all, which is exactly where `new_domain`, `anonymous_employer` and `chat_contact` carry the score. Social posts: "the poster works at that company" (PLAN 4) is not checkable without a login; UNKNOWN, left to the LLM `posterClaimsToBeEmployee` flag at best.
